An MVP is a complete journey, not a small feature list.

Scope a first release around the outcome a real user needs to reach.

Technology / STUDIO NOTES

Choose one user and one outcome

A useful first release should let a specific user finish something valuable. Describe that journey from the moment they arrive to the point they can recognise success. For a booking tool, success might mean choosing an available slot and receiving a reliable confirmation. A dashboard, account system and settings screen are only useful if they support that outcome.

Include the unglamorous states

The happy path is only part of the product. Decide what happens when information is missing, a request fails, a user loses access or a booking changes. These states affect trust even in a small release. Planning them early helps distinguish essential product behaviour from optional polish.

Separate launch needs from future ambitions

Write down the things that must exist on day one, the things that can be handled manually for a limited pilot and the things that can wait. Manual work needs an owner and a clear limit; it should not become an invisible dependency. Keep a separate list of future ideas so that discussing them does not silently expand the current agreement.

Make acceptance observable

Replace “the app should feel professional” with concrete checks: a user can complete the journey on a phone, the correct records are stored, access is limited to the right roles and a failed request explains the next step. Agree who reviews these checks. A narrow product with a complete journey gives a team better evidence than a broad collection of disconnected screens.
